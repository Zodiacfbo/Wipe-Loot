# Wipe & Loot — instructions pour Claude

Deckbuilder roguelite à la Slay the Spire, univers original (Eldrava) inspiré de WoW. TypeScript + Vite, sans framework.
Dépôt : `Zodiacfbo/Wipe-Loot` (l'ancien nom `zodiacfbo/projetwow` redirige encore : si un outil GitHub l'utilise, prendre le nouveau).

## §0 Mes commandes

À rappeler en une ligne au début de toute conversation sur ce jeu :
> Commandes : « Parlons du jeu » · « Publication sur dev » · « Publication sur playtest » · « Publication sur main » · « Fin de discussion »

- **« Parlons du jeu »** : lire les issues GitHub ouvertes et `docs/ROADMAP.md`. Résumer en 5 lignes maximum : où en est le jeu, ce qui est en cours, ce qui attend une décision. Rappeler les commandes, puis demander « De quoi on parle aujourd'hui ? ».

## §1 Règles de travail

- **Toujours répondre en français**, simplement, sans jargon. Réponses courtes par défaut.
- **On discute d'abord, on propose, puis on code.** Pour ce qui touche l'interface, montrer d'abord une maquette (une capture). Pour une classe ou un acte, la fiche dans `docs/` sert de plan.
- **« Pas d'action » ou « on en discute »** veut dire : aucune modification (ni code, ni commit, ni push).
- **Aucune publication sans ma commande explicite** (« Publication sur dev », « Publication sur playtest » ou « Publication sur main »). Une question ou une idée approuvée ne veut pas dire « vas-y ». Seule exception : le CLAUDE.md à la « Fin de discussion ».
- **Secrets :** ne jamais écrire une clé, un mot de passe ou un jeton dans le chat ni dans le dépôt. Il n'y en a aucun pour l'instant. Quand Firebase arrivera (phase 4), ses clés seront gérées à part et ne seront jamais copiées ici.
- Ne pas écrire l'e-mail de l'utilisateur dans le dépôt, ni l'envoyer dans des requêtes extérieures.
- `INSPIRATIONS.md` (anciennes notes privées) n'est plus utilisé : ne pas le recréer ni le demander.
- **Ne jamais mettre le nom du modèle** dans le code, les commits, les issues ou les notes.
- **Pas de pull request** sans que je la demande.
- **Commits :** en français. Ils se terminent par les lignes d'attribution (« Co-Authored-By », « Claude-Session ») données par l'environnement.
- **Commentaires sur GitHub** (issues) : toujours finir par la ligne `_Generated by [Claude Code](https://claude.ai/code)_`.
- **Économiser :** aller droit au but, avec peu d'allers-retours. Opus pour la conception (une nouvelle classe, un nouvel acte), Sonnet ou un effort bas pour les petites retouches. Je regroupe mes demandes dans un seul message.

## §2 Publication

| Branche | Rôle | Adresse |
|---|---|---|
| `dev` | Version de test : tout arrive ici d'abord. | https://zodiacfbo.github.io/Wipe-Loot/dev/ |
| `playtest` | Version des testeurs (les potes) : une copie de `dev` à un moment choisi, **sans l'outil de test**. | https://zodiacfbo.github.io/Wipe-Loot/playtest/ |
| `main` | Version officielle. | https://zodiacfbo.github.io/Wipe-Loot/ |

À chaque push sur `main`, `dev` ou `playtest`, GitHub (`.github/workflows/deploy.yml`) lance les tests, construit les trois versions et les met en ligne. Chaque version a sa propre sauvegarde dans le navigateur (la clé dépend du chemin, `save.ts`). Le fichier de déploiement est celui de la branche poussée : `playtest` étant une copie de `dev`, il a toujours le bon.

**Numéro de version** (`src/version.ts`, rempli par `vite.config.ts`) : affiché en bas du hall, par exemple « v0.1.0 · 23/11/2026 · 1c9c433 · playtest » (numéro du `package.json`, date et code du dernier commit, site). Le numéro du `package.json` se change à la main quand une étape importante est franchie.

**Au début de chaque conversation**, partir de `dev` à jour (`main` est en retard sur `dev`) :
```bash
git fetch origin dev
git checkout -B <branche de session> origin/dev
```

**Avant chaque publication**, tout doit être vert :
```bash
npm test
npm run build
```

**« Publication sur dev »** :
1. Committer sur la branche de session, puis `git push -u origin <branche de session>`.
2. `git fetch origin dev`. Si `dev` a bougé, fusionner `origin/dev` dans la branche, puis relancer les tests et le build.
3. `git push origin HEAD:dev`, en avance rapide uniquement.
4. Vérifier que le déploiement GitHub est passé, puis donner l'adresse.

**« Publication sur playtest »** (seulement des choses déjà publiées sur `dev`) :
1. `git fetch origin dev playtest`. Si `playtest` existe, vérifier qu'il est en retard sur `dev` (`git merge-base --is-ancestor origin/playtest origin/dev`).
2. `git push origin origin/dev:playtest` : `playtest` devient une copie de `dev`, en avance rapide.
3. Vérifier le déploiement, puis donner l'adresse et le numéro de version.

**« Publication sur main »** : pour l'instant, **`main` reste vide** (seulement le premier README). On n'y publiera le jeu qu'une fois la « version 1.0 » définie (ROADMAP, phase 6). Ce jour-là :
1. `git fetch origin main dev`, puis vérifier que `main` est bien en retard sur `dev` (`git merge-base --is-ancestor origin/main origin/dev`).
2. `git push origin origin/dev:main` : `main` devient une copie de `dev`, en avance rapide.
3. Vérifier le déploiement.

**Jamais de `push --force`**, ni sur `dev` ni sur `main`.

## §3 Architecture

### Commandes

```bash
npm test            # vitest (doit rester vert)
npm run build       # tsc + vite build
npx tsc --noEmit -p .
npm run e2e         # test navigateur, PC + téléphone (après npm run build)
bash tools/e2e/cloud.sh   # comptes et sauvegarde en ligne, avec l'émulateur Firebase (Java requis) : 15 vérifications, règles comprises
RUNS=200 PROFIL="Prêtre" npm run balance -- --silent=false  # équilibrage par le bot, avec la marge d'erreur (≈ 1 h par classe ; BOT=simple : l'ancien bot, rapide ; tools/balance/yzhar.sim.ts : Yzhar seul)
cd tools/pixel && python3 illustrations.py                  # régénère les illustrations de cartes
cd tools/pixel && python3 icones_talents.py                  # régénère les icônes de talents sans carte proche
cd tools/pixel && python3 decor.py                           # régénère le décor : feu de camp animé (4 images), icônes repos et enclume
cd tools/pixel && python3 acte3.py                           # sprites des ennemis de l'acte 3 (dont Yzhar), cartes-statut de l'acte
cd tools/pixel && python3 animations.py                      # planches animées (héros, familiers, tous les ennemis) : à relancer après tout nouveau sprite
```

### Le code

- `src/engine/` : moteur **pur et sérialisable en JSON** (RNG déterministe mulberry32 dans `rng.ts`). Aucune dépendance au DOM.
  - `types.ts` (états de run et de combat), `run.ts` (déroulement de la run), `combat.ts` (tours, cartes, ennemis), `actions.ts` (dégâts, blocage, soins, morts).
  - `cards.ts` (Guerrier, cartes-statut, registre `CARDS`), `cards_mage.ts`, `cards_demoniste.ts`, `cards_pretre.ts`, `cards_voleur.ts`, `cards_paladin.ts`, `cards_chasseur.ts`, `cards_druide.ts`, `cards_chaman.ts`.
  - `spells.ts` (sorts de barre de toutes les classes), `talents.ts` (arbres par classe, `CLASS_TREES`), `classes.ts` (fiches et kits de départ).
  - Mécaniques de classe : `demoniste.ts` (familier, DoT, Malédictions, éclats), `pretre.ts` (Égide, Foi), `voleur.ts` (combo, Camouflage, Poison, Contrôle), `paladin.ts` (Sceaux et Jugement, Auras, Censure), `chasseur.ts` (compagnon, Esprits, Pièges, Marque), `druide.ts` (formes, rage de l'Ours, combo du Félin, cartes de forme ; aussi les invocations temporaires `treants`, partagées avec le Chaman), `chaman.ts` (totems, Résonance, Armes élémentaires, Réincarnation).
  - `enemies.ts` (acte 1), `enemies_acte2.ts` et `enemies_acte3.ts` (acte 3 : `burrow`, `resist`, `pierce`), `folie.ts` (Folie, Hallucinations, Crise de folie), `irem.ts` (boss secondaires d'Irem), `yzhar.ts` (Yzhar : Regard sombre, Carapace divine, entrailles), `acts.ts` (registre des actes), `map.ts`, `events.ts`, `items.ts` (objets, tables de loot, `uselessFx` par classe), `potions.ts`, `difficulty.ts` (niveaux 0 à 20).
  - `save.ts` : sauvegarde **versionnée** avec `migrate()` (run) et `loadProfile()` (profil). Tout nouveau champ de `RunState` → incrémenter la version et ajouter une étape de migration, et mettre à jour `expect(run.version)` dans les tests.
  - `talent_icons.ts` : l'icône de chaque talent (illustration d'une carte proche, ou `talent_<id>.png` dessinée par `tools/pixel/icones_talents.py`) et `TALENT_REFS`, les cartes et sorts qu'un talent cite (rappelés dans sa fiche). Un nouveau talent → une ligne ici (vérifié par `tests/talent_icons.test.ts`).
  - `progression.ts` (score, expérience, niveaux ; par classe : victoires `wins` et légendaire forgé `legendary`, retenus depuis novembre 2026), `guild.ts` (coffre), `archives.ts` (lore des monstres).
  - `devtools.ts` : **l'outil de test** (niveaux, remises à zéro, déblocages, triches de run), affiché seulement sur `/dev/` et en local. **À retirer avant la version 1.0** (avec `tests/devtools.test.ts` et les lignes « Outil de test » de `ui.ts` et `style.css`).
- **Comptes et sauvegarde en ligne (Firebase, issue #9)** :
  - `src/cloud.ts` : connexion « pseudo + mot de passe » (le pseudo devient une adresse factice `pseudo@joueurs.wipe-loot.invalid`), copie du profil et de la run dans `sites/{dev|playtest|main}/joueurs/{uid}`, saison lue dans `sites/{site}/config/general`. Firebase est chargé à part (`import()`), seulement si la configuration existe. **Sans configuration (local, tests), tout est désactivé** et le jeu marche comme avant.
  - La sauvegarde du navigateur reste la principale : `save.ts` prévient `cloud.ts` à chaque écriture (`onLocalSave`) ; l'envoi en ligne se fait au changement d'étape (`runStepKey`), quand le profil change et quand on quitte la page. Rien n'est envoyé tant que la saison n'est pas connue (connexion sans réseau).
  - `src/cloud_logic.ts` : les règles sans Firebase (pseudo, messages d'erreur en français, `syncChoice` : appareil ou en ligne à la connexion, saison), testées dans `tests/cloud.test.ts`.
  - `firestore.rules` : les règles de sécurité, **à recoller dans la console Firebase** (Firestore Database → Règles → Publier) à chaque changement. `admin()` attend l'UID de l'organisateur (page admin, plus tard).
  - Configuration : 4 secrets du dépôt GitHub (`FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`, `FIREBASE_APP_ID`), injectés par `deploy.yml` en `VITE_FIREBASE_*`. `VITE_FIREBASE_EMULATOR` ne sert qu'à `tools/e2e/cloud.sh`.
  - Interface : fenêtre de connexion après « Commencer » (maquette B, deux onglets) ; dans le hall, le pseudo et la roue ⚙ (plein écran, mon compte et déconnexion ; news et messages viendront dedans) ; le « ? » reste à part. Message « Nouvelle saison ! » quand la saison change.
- `src/version.ts` : le numéro de version affiché dans le hall (`versionLabel`, `siteOf`), rempli à la construction par `vite.config.ts`.
- `src/ui.ts` : tout l'affichage (HTML en chaînes, délégation d'événements via `data-action`). `src/style.css`. `src/fx.ts` : animations à partir de `c.fx`.
  - `src/keywords.ts` : le lexique des infobulles (mots-clés soulignés dans les cartes, pastilles). Un nouveau mot-clé (Folie, Résonance, Piège…) → une entrée dans `KEYWORDS`. Une pastille avec un `title` garde cette aide précise.
  - `src/tuto.ts` : le **tutoriel**. Textes des bulles : `HALL_STEPS` (visite du hall), `COMBAT_STEPS` (partie commune du combat), `CLASS_STEPS` (3-4 bulles par classe, reprises dans l'encart « Comment ça se joue » de la fiche de classe). Chaque bulle éclaire un élément trouvé par sélecteur CSS (`cible`, du plus précis au plus large). Le profil retient `tuto.hall`, `tuto.classes` (« Compris » par classe) et `tuto.mini`. Un élément d'interface renommé ou déplacé → vérifier les sélecteurs (`TUTO=1 npm run e2e` capture chaque bulle et signale celles qui ne trouvent rien).
  - `src/aides.ts` : les bulles (appui long sur téléphone, survol sur PC ; le clic qui suit un appui long est avalé) et l'aperçu des dégâts sur les ennemis. Le calcul est dans `src/engine/preview.ts` (`previewCard`, `cardHitValue`) : la carte est jouée sur une copie du combat, donc toute nouvelle mécanique est prise en compte sans rien ajouter.
- `tools/balance/` : le bot (`bot.ts`) et les simulations (`*.sim.ts`). En combat, le bot ne regarde qu'une action à l'avance. Hors combat (le « banc d'essai », depuis novembre 2026), il rejoue 3 combats types de l'acte avec chaque option (carte, objet, amélioration, retrait, achat) et garde la meilleure : la même règle pour les 9 classes. `tests/bot.test.ts` vérifie qu'il finit une run avec chaque classe.
- `tools/pixel/` : sprites et illustrations en Python/Pillow (classe `Sprite` dans `sprites.py`). Sortie dans `public/assets/` (`carte_<id>.png`, `ennemi_<id>.png`, `<classe>.png`, `familier_<id>.png`, et le décor de `decor.py` : `feu_camp.png`, `icone_repos.png`, `icone_enclume.png`). `animations.py` exporte les planches animées `anim_<fichier>.png` (4 images côte à côte) : héros et Vulkhar, Vhaeryx, Molosse, Étincelle dessinés à la main (fonction `f`), les autres ennemis par l'animateur automatique `anime_auto` (profils dans `PROFILS`). Le jeu les joue en CSS (`spriteAttrs` et `ANIMES` dans `ui.ts`) ; règles dans `docs/DIRECTION_ARTISTIQUE.md` §7.
- `docs/` : `CONCEPT.md`, `ROADMAP.md`, `EQUILIBRAGE.md` (journal des passes du bot), une fiche par classe (`docs/classes/`) et par acte (`docs/actes/`).

### Ajouter une classe (recette suivie pour les 8 classes après le Guerrier)

1. Lire la fiche `docs/classes/<CLASSE>.md`.
2. `types.ts` : champs de combat (ressource) et de run si besoin (+ migration `save.ts`). `items.ts` : clés `ItemEffects` des talents, `KEY_CLASSES` pour les bonus propres à la classe, et sa famille d'armes dans `WEAPON_FAMILIES` (déjà remplie pour Chasseur, Chaman et Druide ; vérifié par `tests/armes.test.ts`).
3. Mécaniques dans un module `src/engine/<classe>.ts`, branchées dans `combat.ts` (début de tour, `playCard`, fin de tour) et `actions.ts`.
4. `cards_<classe>.ts` (ids uniques ! vérifier les collisions avec `CARDS`), fusion dans `CARDS`. Champ `classId` posé automatiquement. **Textes courts :** 72 caractères au plus (vérifié par `tests/cardtext.test.ts`) ; une explication qui revient va dans un mot-clé (`keywords.ts`) ; un mot de type en tête (« Finisher : », « Sceau : »…) passe dans le bandeau de la carte (`splitRibbon` dans `src/cardtext.ts`).
5. Sorts de barre dans `spells.ts` (+ id du sort de départ dans `lootSpells`), arbres dans `talents.ts` (`CLASS_TREES`), icônes et rappels des talents dans `talent_icons.ts`, kit dans `classes.ts` (`playable: true`, `starterDeck`, `startSpell`, `sprite` : le sprite remplace le « ? » de l'écran des classes), et ses 3-4 bulles de tuto dans `CLASS_STEPS` (`src/tuto.ts`, vérifié par `tests/tuto.test.ts`).
6. Malédiction de lignée de Vhaeryx (`lineageCurse` dans `combat.ts`) et texte dans `ui.ts` (`curseText`).
7. Légendaire et quête (item dans `items.ts`, étapes dans `run.ts`/`events.ts`, bouton au feu de camp dans `ui.ts`).
8. UI : jauge de ressource dans `combatScreen` (voir `demonResource`, `priestResource`), chips, `POWER_LABEL`, préchargement du sprite.
9. Sprite **animé** (fonction de dessin avec `f`, ligne dans `ANIMES` de `tools/pixel/animations.py` et de `src/ui.ts` ; vérifié par `tests/animations.test.ts`) + illustrations (`tools/pixel/illustrations_<classe>.py`, ajouté dans `illustrations.py`).
10. Tests `tests/<classe>.test.ts` ; mettre à jour `tests/classes.test.ts` et le compte de talents dans `tests/talents.test.ts`.
11. Bot : valeur de la ressource dans `evaluate()` ; profils dans `balance.sim.ts`. Cibles (run complète, difficulté 0) : niveau 1 ≈ 0-10 %, niveau 5 ≈ 15-30 %, niveau 10 ≈ 50-75 %. Le palier 5 coûte 3 points : chaque carte épique doit apporter environ +15 à +25 points, et chaque arbre complet (7 + 3) doit se situer à peu près au niveau des deux autres. Le sort de départ est gratuit (comme Charge, Contresort, Pacte de sang, Égide sacrée) et le deck de départ un peu renforcé par rapport à la fiche.
12. Docs : fiche de classe (chiffres retenus + §« Ce qui est en jeu »), `EQUILIBRAGE.md`, `ROADMAP.md`.

### Pièges connus

- Les scripts Python de remplacement doivent vérifier que l'ancre existe une seule fois (un `replace` peut toucher deux lignes du même tableau).
- Ne pas modifier une liste pendant qu'on la parcourt avec un alias (bug déjà vu dans `placeCurse`).
- Les scripts Playwright échouent parfois à cause de la bénédiction tirée au hasard : relancer, ce n'est pas un bug du jeu.
- Un ennemi qui change à un palier (deuxième vie, Copies, adds qui se relèvent) doit compter sa suite dans `evaluate()`, sinon le bot n'ose plus frapper et le combat ne finit jamais (déjà vu : Ossyrax, Méhkar, Vhaeryx). Le banc signale ces « runs bloquées ».
- Un talent qui renforce l'attaque de base du deck de départ (4 copies) vaut beaucoup plus que ses chiffres (déjà vu : Convection, Trait de l'ombre amélioré, Feu intense).
- Le bot ne voit qu'une action à l'avance : certains choix (Pacte de sang, Rôdeur contre les boss, Pierre d'âme, les sorts qui donnent de l'énergie comme Sève vitale, Cri des ancêtres, Totem de mana) sont codés en dur dans `bot.ts`. Un effet qui ne rapporte qu'au tour suivant (totem, piège) doit avoir une valeur dans `evaluate()`, sinon le bot ne le joue jamais.
- Pour équilibrer une classe, isoler un talent ou une carte épique : `simulateRun` accepte n'importe quelle liste d'ids de talents (ex. `['t_avatar_lumiere']` seul au niveau 1). Ne pas garder ces sondes dans le dépôt.
- Le jeu se joue en paysage : dans Playwright, utiliser `devices['iPhone 13 landscape']` (en portrait, un écran « tourne ton téléphone » bloque les clics).

## §4 Tester

1. **Tests automatiques** : `npm test` et `npm run build`, toujours verts avant une publication. Une nouvelle mécanique = de nouveaux tests.
2. **Équilibrage par le bot** : seulement la classe ou l'acte concerné (ex. `RUNS=200 PROFIL="Voleur" npm run balance -- --silent=false`). À 100 runs la marge est de ± 10 points, à 200 de ± 7 : 100 runs pour chercher, 200 pour confirmer. Pour isoler un talent ou une carte épique, une sonde jetable (non gardée) qui lance `simulateRun` sur plusieurs profils en parallèle. Noter le résultat dans `docs/EQUILIBRAGE.md`.
3. **Navigateur, une seule fois à la fin** : `npm run build`, puis `npm run e2e` (script `tools/e2e/parcours.cjs`, captures dans `tools/e2e/captures/`, ignorées par git). Il fait le parcours **sur PC et sur téléphone** : Commencer → choix de la classe → hall de la guilde (visite guidée, bulle par bulle) → Partir en expédition → Brégan → carte → premier combat (tuto du « ? », bulle par bulle), et échoue si une étape manque ou si la page montre une erreur JavaScript. Options : `CLASSE=mage`, `ECRANS=telephone`, `URL=…` (serveur déjà lancé).
   Pour tester un écran précis (vendeur, feu de camp, butin) : générer un état de run avec un test vitest jetable, l'écrire dans un fichier JSON, puis `ETAT=fichier.json npm run e2e` (la run est ouverte depuis le hall, capture « etat »). Un état mal préparé donne un écran vide : le script le signale.

## §5 Où en est le projet

- **Joueurs :** moi, puis les potes sur `/playtest/`. **Comptes en ligne (23 novembre 2026, étape 1 de l'issue #9)** : pseudo + mot de passe, sauvegarde copiée en ligne, saison. Restent (issue #9) : journal des runs et page admin, bugs et messages, news, stats et modération.

L'outil de test lance les boss d'Irem et Yzhar depuis la carte. Ensuite l'acte bonus (Nécropole céleste).
- **Légendaires faits (tous) :** Brisemonts (Guerrier), Bâton du Veilleur (Mage, Démoniste, et Druide : rendre un objet à la terre), Équinoxe (Prêtre), Sillon d'orage (Voleur, chez l'événement Ventor), l'Aurore ardente (Paladin : Reliquaire profané, puis Ossyrax et le feu de camp, ou les Veilleurs de l'Aurore et un boss secondaire d'Irem), Corde-des-anciens (Chasseur : le vieux trappeur, les Trois Souffles, le feu de camp), le Marteau des ancêtres (Chaman : le Cercle des anciens, Skarn, puis le combat de « L'appel des éléments »). Ils se forgent à partir de l'acte 2.

  - Fiche à droite : talents, classes (avec « Ta progression »), équipement (héros entouré de ses 6 emplacements), archives (grille par groupes, % par onglet), coffre détaillé et tables de loot.
  - Fiche en fenêtre : vendeur (« Acheter · X or », y compris pour les cartes) et confirmations de carte définitives (retirer, Allègement, sacrifice du Bâton).
  - Feu de camp : scène (héros + feu animé) et choix en tuiles ; repos grisé si PV pleins. Deck et choix de carte : copies regroupées « ×N ». Hall : coffre en icônes, description de la classe jouée ; les boutons de classe en texte restent (choix de l'utilisateur).
  - Boutons de sortie : écrans pleins du hall → « Retour » en haut à droite ; fenêtres et écrans d'expédition → bouton en bas.
  - Premier lancement : l'accueil présente le jeu (sous-titre « Un jeu de cartes et d'aventure au royaume d'Eldrava », accroche « Tomber, se relever, et rapporter le butin. », 4 tuiles), puis le choix de la classe, puis le hall (pas directement en expédition).
  - **Tutoriel (novembre 2026, `src/tuto.ts`)** : visite du hall en 6 bulles, lancée toute seule la première fois (« Passer » discret), revue avec le « ? » du hall. Tuto du combat seulement avec le « ? » de la barre du haut : 10 bulles communes puis 3-4 bulles de la classe ; il montre le combat en cours sans rien forcer. Le « ? » brille jusqu'au « Compris » (pas « Passer »), pour chaque classe ; mini-bulle la première fois ; une nouvelle classe ne montre que sa partie (« Tout revoir »). Style des bulles : écran assombri sauf l'élément montré.
  - Fiche de classe : encart « Comment ça se joue » (les bulles de la classe), portrait réduit pour que le bouton reste visible sur téléphone. La citation et la description sont retirées pour l'instant : je réécrirai la présentation de chaque classe avec mes mots.
  - Combat : infobulles des mots-clés (mots en or, soulignés seulement au survol, et pastilles ; appui long sur téléphone, survol sur PC ; l'appui long sur une carte la décrit sans la jouer) et aperçu des dégâts (chiffre corrigé sur la carte, PV perdus et « Achevé » sur les ennemis ; rien quand le résultat dépend du hasard).
  - Cartes (novembre 2026) : textes de 72 caractères au plus. Le chiffre corrigé montre le total, puis la formule entre parenthèses : « 22 dégâts (4 + 6 par combo) » (`placeHit` dans `src/cardtext.ts`). Le bandeau affiche Finisher, Sceau, Aura, Ouverture ou Poison d'arme à la place du type ; l'appui long donne le vrai type. Un mot-clé `discret` (« combo ») n'est pas souligné mais reste expliqué à l'appui long sur la carte. Une carte grisée dit pourquoi quand on la touche (`cardBlockReason`) ; une carte dont la condition est remplie brille (`cardReady` dans `src/engine/hints.ts`) ; une amélioration montre en vert ce qui change (`markDiff`). Archives : onglet glossaire. Deck : filtre par type et tri.
- **Animations (novembre 2026) :** les 9 héros (le Prêtre change de tenue en Forme d'Ombre, le Druide à chaque forme, avec un flash), les 5 familiers, les 3 compagnons du Chasseur et tous les ennemis sont animés au repos, style « marqué » comme le feu de camp (4 images, 0,2 s chacune). Arrêt sur image et flash blanc à l'impact (`hitStop` dans `fx.ts`). **Règle :** tout nouveau sprite (classes restantes, acte 3, acte bonus) est animé dès sa création ; un ennemi ou une classe jouable sans planche fait échouer les tests. Restent : les poses d'action (élan, coup reçu, incantation, mort) et des retouches à la main des boss secondaires.
- **Profil :** les niveaux de difficulté débloqués et les talents sont propres à chaque classe ; le hall retient la dernière classe choisie.
- **Armes jumelles (novembre 2026) :** chaque arme de boss existe en mêlée (Attaques) et en incantation (Sorts), au même effet ; un boss donne la version de ta famille (`WEAPON_FAMILIES`, `WEAPON_TWINS`, `itemFor`), et ne fait jamais tomber un objet inutile à ta classe (`rollTable`). Détail dans `CONCEPT.md` §12.2. Une nouvelle arme de boss → sa jumelle.
- **Râtelier :** le légendaire forgé (`legendary` du profil, par classe) est emporté par défaut depuis le hall (`newRun(…, legendary)`), en plus d'un objet du coffre qui n'est alors pas une arme ; sa quête passe à « forged » pour l'expédition (`LEGENDARY_QUEST` dans `run.ts`). ## §6 Façon de travailler

- **Une conversation courte par chantier**, fermée par « Fin de discussion ».
- **Tout ce qui doit survivre est écrit** dans les issues, les docs et ce CLAUDE.md, jamais seulement dans la conversation.
- **Un seul chantier à la fois.**
- Quand je dois choisir une interface : proposer **2 ou 3 variantes de maquette d'un coup**.
- Pendant un travail en cours, **ne pas répondre à côté** : finir ou demander, sans partir sur autre chose.
- Les issues GitHub : « 💡 Idées pour plus tard » (le carnet d'idées : une idée = un commentaire), « 🔒 Sécurité et triche », « 🗣️ Vocabulaire du jeu » (#8), et une issue par gros chantier.

## §7 Mes habitudes

- Pour une décision : les avantages et les inconvénients, puis un avis clair (« Mon conseil : … »).
- Penser aux **joueurs moins forts**, aux **petits écrans** et à la **lisibilité**.
- **Ne pas ajouter de nouveautés pour en retirer d'autres** : on garde ce qui existe, on ajoute seulement quand c'est utile.
